```
【サーバー】

【Web / アプリ】
・React 19 + Vite … スマホの「縄を引く」画面、ホスト管理画面、席画面、プロジェクター画面
・qrcode … 席ごとの参加用 QR コード生成（スマホで読むだけで着席）
・Tauri 2 … 同じ Web コードを iOS / Android ネイティブアプリとしてビルド
・Playwright … 偽プレイヤー 4 人 + 偽 ESP32 による E2E テストとスクリーンショット自動生成

【ハードウェア / ファームウェア】
・Arduino core for ESP32（Espressif）… ESP32 のファームウェア開発

・Wire（I2C）… MPU6050（IMU）のジャイロを読んで方位（yaw）を推定・サーバーへ報告
```

## 4) 技術的に工夫した点・苦労した点 *

▼ コピペ用

```
【工夫した点】
・合力で動く「引っ張り合い」: 4 人のスマホの引く強さ（縄のドラッグ量）を各席方向の単位ベクトルに掛けて合算し、
  皿はその合力の向きへ進む。向かい合う同じ強さは打ち消し合うので、ただ強く引くだけでは勝てず、
  「遠慮」と「駆け引き」が生まれる。拮抗判定・減衰（粘り）・速度ゲイン等の係数はホスト画面から本番中に調整可能。
・リアルタイム同期: Cloudflare Durable Objects で 1 部屋 = 1 インスタンスにし、WebSocket で全端末へ状態配信。
  サーバー 1 つで物理状態を一元管理し、スマホ・実機・観戦画面がすべて同じ状態を見る。
  クライアント側は 2Hz の状態を 60fps で補間してなめらかに表示。
・実機とクラウドの直結: ESP32 が WSS でサーバーへ常時接続し、forward / turn_right 等のコマンドを受信。
  一定時間コマンドが来なければ自力で停止するフェイルセーフ、誰でも叩ける緊急停止 API を用意し、安全側に倒した。
・方位のズレ対策: タイヤ皿は向きの推定がずれやすいため、IMU（MPU6050）の yaw をサーバーへ報告して方位を補正。
  IMU が無くても動くよう推測航法にフォールバックし、旋回速度のキャリブレーション機能も実装。
・3 つの出力モード: A=タイヤ付き実機の皿、B=テーブル下の磁石 XY ステージ、C=画面上の仮想皿。
  ゲームロジックは共通で、モード別アダプタで各デバイス向けの値に変換。ハードが不調でもその場で切り替えてデモ継続可能。
・デモ運営のための画面: 部屋コードを固定し、/host のホスト管理画面（状態監視・開始/停止・緊急停止・手動操作・
  キャリブ・係数調整・イベントログ・BOT プレイヤー）、/a〜/d の席画面（QR を読むだけで着席）、
  /stage のプロジェクター用観戦画面を用意。
・1 つのコードで Web / iOS / Android: Tauri 2 で同じ React コードをネイティブアプリ化。
・AI エージェント駆動開発: Claude Code で設計案を作り、Claude Code / Codex に複数タスクを並列で実装させ、
  E2E テスト（偽プレイヤー + 偽 ESP32）で自動検証してから main に push → 自動デプロイ、という流れで短時間に多機能化。

【苦労した点】
・実機の皿は「どっちを向いているか」が分からないとまっすぐ進めない。推測航法だけでは旋回のたびにずれていくため、
  IMU による補正と旋回キャリブレーションを後から追加した。
・ネットワーク越しの実機制御の安全性。通信が切れても暴走しないよう、ファーム側のタイムアウト停止と
  サーバー側の緊急停止を二重にした。
・モード切替まわり: 仮想モードのままだと実機にコマンドが届かない問題があり、ESP32 接続時に自動で実機モードへ切り替えるようにした。
・Tauri の iOS ビルドで、アプリ名（productName）が日本語だと Xcode のビルドが通らず、ASCII 名（EnryoKiller）に変更して解決。
【要確認：ハード側で苦労した点（モーター・電源・配線・磁石の吸着力など）を 8no に追記してもらう】
```
